# Design REQ-002: offline bounce

Architect, 2026-10-24. Status: **approved by the architect (option a), awaiting the user.**
Inputs: `requests/REQ-002-rec-bounce.md`, `detailed/RECc.md`, design REQ-001.

## Problem

`bounce <seconds> [path]` should render audio to a file faster than real time.
After R1, the Conductor lives inside the cpal callback, so the REPL thread
can't call `render` itself.

## Options and costs

**(a) Render ahead inside the callback, with live output muted** (RECc).
- While a bounce runs, each callback renders up to `BOUNCE_BLOCKS` device-sized
  blocks into the recording ring (REQ-001), only when the ring has room for a
  whole block, then fills the device buffer with zeros.
- It stops exactly at the frame count, then retires the producer and emits
  `BounceDone`.
- Cost: S, about 120 lines in REC's own files, plus 4 registry entries. No
  new thread, queue or global beyond REQ-001.
- Behaviour cost: live output is silent during the bounce, and the session
  is N seconds further on afterwards.

**(b) A second Conductor on a bounce thread.**
- It needs the sample clock and rate moved out of process-wide statics
  (`blast_time.rs`), which touches E1, TMP, PRC and every process.
- It also needs a mirror-to-engine rebuild, and still can't reproduce
  run-time state (play positions, tempo phases, RNG).
- Cost: L–XL, and it changes §3.4. It's also the wrong result: it would
  render a different session from the one that's playing.

**(c) Out of scope.** Zero cost. Users capture with `rec` in real time.

## Recommendation: (a)

(b) is rejected: its cost is large and its result is worse. Between (a) and
(c): (a) is cheap, adds nothing architectural beyond REQ-001, and renders
exactly what the session would play. Its semantics (muted live output, the
session advancing) are a user-facing trade-off, so the user should confirm
them. If they're unwanted, (c) is the fallback, and RECc is withdrawn.

Conditions on RECc (required fixes in the plan):
1. **Never drop and never allocate.** This is already in the plan (it waits
   for whole-block room, and uses the device buffer as scratch). Keep it.
2. **Bound the callback's work.** A fixed `BOUNCE_BLOCKS = 8` can push heavy
   sessions past the deadline every period. The xruns are inaudible, but
   R1 surfaces stream errors as events, and they could flood the event
   queue. Either:
   - coalesce: R1/E1 events already drop when the queue is full, so this only
     needs RECc's manual check to confirm the REPL isn't spammed; or
   - (preferred) make the loop time-budgeted: stop rendering extra blocks once
     `Instant::now()` (vDSO `clock_gettime`, no allocation, lock or syscall on
     Linux) passes about 50% of the period's duration, with `BOUNCE_BLOCKS` as
     the upper bound.
   The implementer reports the speed and xrun behaviour on the dev machine.
3. **`rec stop` ends a bounce early**, and `rec`/`bounce` exclude each other
   in the mirror (already planned via `TakeMode`).
4. **The test twin's limits are documented.** The plan does this: comparing
   with a twin Conductor only works for tempo-free voices, because the clock
   is global.

## Exact README changes (after the user approves)

Append to the new §3.10 (REQ-001):
> - `bounce <seconds> [path] [--bits 16|24]`: `Command::Bounce(BounceArgs { producer, frames })`.
>   While `frames` remain, each `render` call renders up to `BOUNCE_BLOCKS`
>   extra device-sized blocks of the live session into the take's ring (only
>   when a whole block fits, so a bounce is gapless), outputs silence, and
>   ends with `Event::BounceDone`. Live time advances by the bounced length.

## Effect on briefs, ownership, plans

- Briefs: none (`PJ-recording.md` already lists the options).
- Ownership: none. RECc uses RECb's files.
- Plans: RECc as written, plus condition 2. If the user picks (c), RECc is
  withdrawn, and RECa/RECb are unaffected.
- E1/R1: nothing beyond REQ-001 (the clock advances inside `render`; events
  drop when full).
