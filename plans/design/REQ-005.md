# Design REQ-005: Shell API additions (README §3.7)

Architect, 2026-10-24. Status: **approved by the architect (option 1, with
two amendments), awaiting the user.**
Inputs: `requests/REQ-005-shell-api-additions.md`, `detailed/SHb.md`,
`detailed/REPLb.md` (the consumer).

## Problem

§3.7 fixes only `Shell::feed` and `ShellOut`. To integrate the shell, REPL
also needs to:
- know whether a block is open (for the continuation prompt),
- drop an open block (Ctrl-C),
- run a script file (`--script`, `source`),
- get names for completion,
- find the start of a command segment,
- convert a `Wait` to wall time.

It also needs the concrete `Wait` and `ShellErr` types.

## Options

1. **Additive methods, with `source` expanded inside the shell through a
   loader** (the planner's proposal). Variables and functions from sourced
   files persist. Nesting and cycle limits, and error locations, live in one
   place. The shell does file I/O at `feed` time on the calling thread,
   which is REPL-side and never the audio thread. Cost: none beyond SHb.
2. **`ShellOut::Source(path)`, resolved by REPL.** This changes the §3.7 enum.
   REPL would have to feed the file back into the same shell and track depth
   and locations itself. More coupling, and no gain.

## Recommendation: option 1, with two amendments

1. **Split `names()`.** REPLb's completion needs variables (after `$`)
   separately from functions (first word). So the API is
   `var_names(&self) -> Vec<String>` and `fn_names(&self) -> Vec<String>`,
   both sorted. A single mixed list can't serve REPLb step 7.
2. **`source` takes a path:** `Shell::source(&mut self, path: &Path)`.
   REPL's `Options.script` is a `PathBuf`, and §1.3 says to borrow.

## Exact README §3.7 text (applied after the user approves)

Replace the code block in §3.7 with:
```rust
pub struct Shell { /* variables, functions, open block, loader */ }   // Send
pub type Loader = Box<dyn FnMut(&Path) -> io::Result<String> + Send>;
impl Shell {
    pub fn new() -> Self;                                   // loader = fs::read_to_string
    pub fn with_loader(loader: Loader) -> Self;
    /// Feed one input line. Returns finished output, or nothing while a block is still open.
    pub fn feed(&mut self, line: &str) -> Result<Vec<ShellOut>, ShellErr>;
    /// Expand a whole script file (what `source` does; used for `--script`).
    pub fn source(&mut self, path: &Path) -> Result<Vec<ShellOut>, ShellErr>;
    pub fn pending(&self) -> bool;                          // a statement is still open
    pub fn reset(&mut self);                                // drop it (Ctrl-C)
    pub fn var_names(&self) -> Vec<String>;                 // sorted, for completion
    pub fn fn_names(&self) -> Vec<String>;
}
pub fn command_start(line: &str, cursor: usize) -> usize;   // byte offset of the current simple command
pub enum ShellOut { Line(String), Batch(Vec<String>), Wait(Wait), Print(String) }
pub enum Wait { Millis(f64), Beats { beats: f64, bpm: f64 } }   // + fn duration(&self) -> Duration
pub struct ShellErr { pub src: String, pub line: u32, pub col: u32, pub kind: ShellErrKind }
```
And add after it:
> The shell expands `source` itself, through its loader, at `feed`/`source`
> time, on the calling (REPL-side) thread. A script expands up front into a
> finite list of outputs. Running them, including `Wait`s, is REPL's job, on a
> script thread.

## Effect on briefs, ownership, plans

- Briefs: none. PF's brief already gives REPL the runner.
- Ownership: none.
- **SHb:** rename `names` → `var_names` + `fn_names`, and make `source` take
  `&Path`. Editorial once this is approved.
- **REPLb:** use `var_names`/`fn_names` in step 7, and `source(&path)` in
  step 5. Editorial.
